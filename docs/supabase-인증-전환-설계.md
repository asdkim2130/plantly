# 인증 전환 설계 — 관리형 IdP(Supabase Auth) 도입

- **작성일:** 2026-07-23
- **대상 독자:** 개발자 (본인)
- **상태:** 제안/설계 (착수 전)
- **목적:** 자체 세션 기반 인증을 관리형 IdP로 전환하기로 한 배경·결정·아키텍처·마이그레이션 순서를 한 문서로 고정한다.
- **표기:** ✅ 결정됨 · 🔜 예정/후속 · ❓ 미결정(착수 전 확정 필요)

> 이 문서는 **인증(authentication)** 전환만 다룬다. **인가(authorization)** — 역할·회사 소유권 등 — 는 바뀌지 않으며, 그 이유는 8·15절에 있다.

---

## 1. 배경 & 문제

- 현재: Spring Security **세션 + CSRF** 기반 자체 회원가입/로그인. `User`에 해시 비밀번호 보관. `UserPrincipal` + `@AuthenticationPrincipal`로 컨트롤러에 주입.
- 요구: 유저가 **각자 보유한 이메일(구글·MS·회사 메일)로 별도 가입 없이 로그인**하고, 우리는 **비밀번호 해시와 인증 플로우를 직접 보관·운영하지 않기를** 원한다.
- Company 도메인 구현은 완료 상태이며, **다음 도메인 착수 전**이 전환 적기다.

---

## 2. 결정 요약

| 상태 | 내용 |
|---|---|
| ✅ | 인증을 **관리형 IdP로 외주**한다. 프로바이더는 **Supabase Auth**로 시작. |
| ✅ | 백엔드는 IdP 발급 **JWT를 검증하는 Resource Server**가 된다. 세션+CSRF → **베어러 토큰**으로 전환. |
| ✅ | **클린 컷오버.** 런칭 전이라 기존 계정을 모두 폐기하고 새 모델로 재출발한다(이관 없음). |
| ✅ | **로컬 `User` 행은 유지**한다. 오프로드되는 것은 **크리덴셜과 인증 플로우**이지 유저 레코드가 아니다. |
| ✅ | **인가(역할·소유권)는 계속 내 DB 소유.** 토큰의 role은 신뢰하지 않는다. |

---

## 3. 목표 / 비목표

**목표**
- 별도 가입 없이 구글/MS/임의 이메일로 로그인 (JIT 프로비저닝)
- 비밀번호 해시·MFA·매직링크/OTP를 **직접 보관·운영하지 않음**
- Company 도메인(소유권·역할·인가)에 영향 0

**비목표 (Non-goals)**
- 🔜 **고객사별 엔터프라이즈 SSO**(각 회사가 자기 IdP로 로그인, SAML/SCIM) — 지금은 안 함. 실제 대기업 요구가 생기면 그때 WorkOS/Auth0 검토. "대기업이 자체 메일로만 가입"은 그 회사 이메일을 신원으로 받으면 되는 일반 케이스라 여기 해당 없음.
- 🔜 네이버·카카오 등 추가 소셜 — B2B라 보류.

---

## 4. 대안 비교

| 방식 | 비번 보관 | 인증 플로우 운영 | 세션→JWT 대공사 | 판정 |
|---|---|---|---|---|
| **A. 자체 인증 유지** | 함 | 함 | 없음 | ❌ 요구("비번 안 들기")와 배치 |
| **B. 가벼운 길** — Spring `oauth2-client`(구글/MS) + 매직링크 **직접 구현**, 세션 유지 | 안 함 | **함**(매직링크 이메일·OTP·MFA 직접) | 없음/작음 | △ 세션 유지 이점, 그러나 가장 손 많이 가는 부분을 계속 운영 |
| **C. 관리형 IdP** — Supabase가 소셜·매직링크·MFA 운영, 백엔드는 Resource Server | 안 함 | **안 함** | **있음** | ✅ 채택 |

- **A vs C 갈림 기준:** "매직링크/OTP/MFA까지 직접 운영하기 싫다" → C. 요구가 그쪽이라 C.
- **B를 안 고른 이유:** B도 "비번 0"은 되지만, 이메일 전송·OTP 보안·MFA라는 **가장 함정 많은 부분을 여전히 내가 운영**한다. 오프로드가 목적이면 끝까지 간다.

## 5. 프로바이더 선택 — Supabase Auth

| 상태 | 내용 |
|---|---|
| ✅ | 구글·Azure(Entra)·이메일 OTP/매직링크를 기본 제공, **저비용**, JWT Resource Server 연동이 표준적. |
| ✅ | 인가를 내 DB가 소유하므로 **IdP 교체 비용이 작다** — 나중에 갈아끼우기 쉬움. |
| 🔜 | 엔터프라이즈 SSO가 실제로 필요해지면 **WorkOS/Auth0**를 얹거나 이전. |
| ❓ | 서명 방식 — **비대칭 서명 키(JWKS) 우선**(백엔드가 공개키로만 검증, 시크릿 미보관). 레거시 프로젝트는 공유 HS256일 수 있으니 대시보드에서 확인. |

---

## 6. 아키텍처 개요

**요청 흐름 (로그인 후 API 호출)**

1. 프론트가 Supabase JS SDK로 구글/MS/매직링크 로그인 → **access token(JWT)** 획득. 토큰 갱신도 SDK가 처리.
2. 프론트가 API 호출 시 `Authorization: Bearer <JWT>` 첨부.
3. 백엔드(Resource Server)가 **JWKS로 JWT 서명·만료 검증**.
4. `JwtAuthenticationConverter`(또는 얇은 필터)가 **JWT의 `sub` → 로컬 `User` 조회/JIT 생성 → 기존 `UserPrincipal` 빌드**.
5. 이후는 지금과 동일 — `@AuthenticationPrincipal UserPrincipal`, `@PreAuthorize`가 그대로 동작.

**핵심 seam:** 4번. `UserPrincipal`을 경계로 두면 그 뒤(세션→JWT)만 갈리고 **컨트롤러·도메인은 한 줄도 안 바뀐다.**

## 7. 데이터 소유 경계 (무엇을 어디에 두나)

| 구분 | 필드 | 근거 |
|---|---|---|
| **반드시 로컬 (내 DB 소유)** | `id`(bigint) | 도메인 앵커 — CompanyMember·소유자·verification·draft가 참조 |
| | `authSubject`(= JWT `sub`) | IdP 신원과 잇는 조인 키. **이메일이 아니라 이걸로 유저 키잉** |
| | `role`(MEMBER/ADMIN) | 인가는 내 개념. 토큰에서 안 받음 |
| | `status`(ACTIVE 등) | 계정 라이프사이클·차단 |
| **캐시 (IdP가 원본, 로컬은 사본)** | `email`, `name` | 조회/표시/알림/관리자 검색용. **로그인 때 claim에서 갱신** |
| **앱 전용 프로필 (IdP가 안 줌)** | `phone`, 약관동의 등 | 소셜 로그인이 안 주므로 내가 수집 |
| **IdP 전용 (저장 금지)** | 비번 해시, MFA, 소셜 토큰 | 오프로드 대상 |

> **email 캐시 결정:** 순수 최소주의(claim에서 매번 읽기)는 PII 노출면을 줄이지만 "이메일로 유저 검색·발송"이 불가해진다. B2B 관리자 기능을 고려해 **email·name은 캐시**한다. 사라지는 실질은 "비번 해시 + 인증 플로우"다.

## 8. `User` 엔티티 변경

- ✅ `password` **제거**, `PasswordEncoder` 제거.
- ✅ `authSubject` **추가 (unique)** — 유저 키잉/JIT 조인.
- ✅ `email`·`name` 유지(캐시), `role`·`status` 유지.
- ✅ `id`(bigint)는 **불변 내부 FK** — 도메인 참조 그대로.
- ❓ `phone` — 소셜은 안 주므로 아래 둘 중 택1 (14절).

---

## 9. 보안 원칙

| 상태 | 내용 |
|---|---|
| ✅ | **권한은 토큰이 아니라 로컬 `User.role`에서.** `@PreAuthorize`의 authority는 DB에서 붙인다. |
| ✅ | 유저 키는 **`sub`**(안정적). 이메일은 바뀔 수 있어 조인 키로 쓰지 않는다. |
| ✅ | JWT는 **JWKS 공개키 검증**, `issuer`/`aud`/만료 확인. 백엔드는 서명 시크릿을 보관하지 않는다. |
| ✅ | 베어러 토큰 API이므로 **CSRF는 API 인증에서 제거**한다. |

---

## 10. 마이그레이션 순서 (클린 컷오버)

1. ✅ **`User` 엔티티 정리** — `password` 제거, `authSubject` 추가.
2. ✅ **Resource Server + `UserPrincipal` seam** — `oauth2-resource-server` 추가, JWKS 설정, JWT→UserPrincipal 컨버터.
3. ✅ **JIT 프로비저닝 + 권한 매핑** — 미등록 `sub` 최초 요청 시 User 생성(MEMBER/ACTIVE), role을 authority로.
4. ✅ **테스트 하네스 교체** — 세션 헬퍼(`issueCsrfToken`/`login`/`signUpMember`)를 **테스트 JWT 발급 헬퍼**로 (12절).
5. ✅ **레거시 제거** — 세션 SecurityConfig, 가입/로그인/CSRF 엔드포인트, remember-me, `PasswordEncoder` 삭제.

## 11. 프론트 (참고)

- Supabase 대시보드에서 **Google + Azure 프로바이더 활성화**, 매직링크/이메일 OTP는 기본 내장.
- 프론트는 Supabase JS SDK로 로그인·토큰 갱신, API엔 `Bearer` 토큰만 첨부.
- 필요 키: 프로젝트 URL, anon key(프론트). 백엔드는 인증 검증에 service_role 키 불필요.

---

## 12. 테스트 영향

- ✅ 인수 테스트의 `issueCsrfToken`/`login`/`signUpMember`(세션 기반) → **테스트 프로파일에 신뢰하는 test JWK를 심고 인메모리로 토큰을 발급**하는 헬퍼로 교체.
- ✅ 각 테스트의 **로직·단언은 유지**, 세션 획득부만 토큰 획득부로 치환. (최근 작성한 draft 인수 테스트 포함)
- ✅ 슬라이스 테스트의 `SecurityContext` 수동 주입 방식은 대체로 유지 가능(주입 principal이 UserPrincipal이라).

## 13. 리스크 & 완화

| 리스크 | 완화 |
|---|---|
| **가용성 커플링** — IdP 장애 시 로그인 전면 중단 | 인가는 로컬이라 조회성 트래픽은 영향 적음. SLA/상태 모니터링 확인. 교체 용이성(인가 로컬 소유)으로 락인 완화 |
| **데이터 레지던시(PII)** — 이메일이 IdP 리전에 저장 | ❓ Supabase 프로젝트 **리전 선택** 확인(한국 고객사 PIPA 질의 대비) |
| **벤더 락인** | `UserPrincipal` seam + 로컬 인가로 이전 비용 최소화 |

## 14. 미결정 / 오픈 이슈 (착수 전 확정)

| 상태 | 항목 | 메모 |
|---|---|---|
| ❓ | **`phone` 처리** | (a) `phone` nullable로 완화, 또는 (b) JIT 직후 **"프로필 완성" 스텝**에서 수집. B2B 연락 필요성 있으면 (b) 권장 |
| ❓ | **첫 ADMIN 부트스트랩** | 관리자도 소셜/매직링크 로그인 → JIT로 MEMBER 생성 후 **DB에서 ADMIN 승격**. 초기 승격 방법(수동 SQL/시드) 결정 필요 |
| ❓ | **서명 방식 확인** | JWKS(비대칭) vs 레거시 HS256 — 대시보드 확인 후 설정 확정 |
| ❓ | **Supabase 리전** | PII 저장 위치 확정 |

## 15. 변경되지 않는 것

- ✅ **Company 도메인 전체** — 소유권(CompanyMember), 역할 사용처, `@PreAuthorize`, 상세/검색/수정/임시저장 로직.
- ✅ **`User.id` 기반 모든 FK** — verification·draft·member·소유자 참조.
- ✅ **인가 규칙** — MEMBER/ADMIN, 소유자 접근제어.

> 요지: **인증만 갈리고 인가는 그대로.** 그래서 blast radius가 `UserPrincipal` 뒤로 한정되고, 나중에 IdP를 갈아끼워도 비용이 작다.

[[overview]]
== 개요

Plantly 서비스의 REST API 명세서입니다.
모든 응답은 아래 공통 래퍼(`ApiResponse`) 형태로 내려갑니다.

[[overview-response-wrapper]]
=== 공통 응답 형식

[cols="2,1,5"]
|===
| 필드 | 타입 | 설명

| `success` | `boolean` | 요청 성공 여부
| `message` | `string` | 성공 메시지 (성공 시, 없을 수 있음)
| `data`    | `object` | 응답 데이터 (성공 시, 없을 수 있음)
| `error`   | `string` | 에러 메시지 (실패 시에만 존재)
|===

NOTE: `ApiResponse` 는 `@JsonInclude(NON_NULL)` 이므로 값이 `null` 인 필드는 JSON 응답에서 생략됩니다.
예를 들어 회원가입 성공 응답에는 `data`/`error` 가 나타나지 않습니다.

[[overview-auth]]
=== 인증 / 보안 공통 규약

세션 기반 인증을 사용합니다. 인증 메커니즘은 전역 공통 규약이므로 각 API 문서에 반복하지 않고 여기에 한 번만 명시합니다.

* *로그인*: `POST /api/v1/auth/login` 성공 시 `JSESSIONID` 세션 쿠키가 발급됩니다.
  이후 인증이 필요한 요청에는 이 세션 쿠키가 자동으로 동봉되어야 합니다.
* *CSRF*: 상태를 변경하는 모든 요청(`POST`, `PATCH`, `PUT`, `DELETE`)은 CSRF 보호를 받습니다.
  먼저 `GET /api/v1/auth/csrf` 로 토큰을 발급받은 뒤, 발급된 값을 `X-XSRF-TOKEN` 요청 헤더에 담아 보내야 합니다.
  누락 시 `403` 이 반환됩니다.
* *인증 실패*: 미인증 상태로 보호 자원에 접근하면 `401`, 권한이 부족하면 `403` 이 반환됩니다.

[cols="2,1,5"]
|===
| 항목 | 위치 | 설명

| `JSESSIONID` | Cookie | 로그인 시 발급되는 세션 쿠키 (인증 필요 API 필수)
| `X-XSRF-TOKEN` | Header | CSRF 토큰 (변경 요청 필수)
|===

[[company]]
== 회사 (Company)

[[company-verification]]
=== 사업자 인증 (선행 인증)

회사 등록 *전에* 국세청 사업자등록정보로 사업자 진위를 확인합니다. 회원가입의 아이디 중복 확인처럼 등록 폼 앞단에서 먼저 수행합니다.

서버는 세 단계를 한 번에 처리합니다.

. *진위확인* — 사업자등록번호·대표자명·개업일자 조합이 국세청 등록 정보와 일치하는지 확인
. *상태조회* — 계속사업자인지 확인 (진위확인만으로는 폐업자를 걸러내지 못합니다 — 폐업해도 등록 이력이 남아 일치 판정이 납니다)
. *중복 검사* — 활성 회사 중 같은 사업자번호가 이미 있는지 확인

통과하면 `verificationId` 를 발급하고, 이 식별자를 <<company-create>> 요청에 실어 보내면 서버가 검증된 값을 채웁니다.
등록 요청에는 사업자번호·대표자명·개업일자 자리가 아예 없으므로, 인증받은 값과 다른 값이 저장될 수 없습니다.

CAUTION: `businessStartDate` 는 *개업일자* 입니다(사업자등록증 기준). 법인 등기 설립일과 다를 수 있으며, 국세청은 개업일자로만 대조합니다.

인증은 발급 후 *30분* 간 유효하며, 한 번 등록에 사용하면 재사용할 수 없습니다.
남용과 국세청 일일 쿼터 보호를 위해 사용자당 *하루 5회* 로 시도를 제한합니다(국세청 장애로 판정을 못 받은 시도는 차감하지 않습니다).

[cols="2,1,4"]
|===
| 사유 | 상태 | `error` 메시지

| 사업자번호 형식 오류 (숫자 10자리 아님)
| `400`
| 사업자등록번호는 숫자 10자리여야 합니다.

| 진위 불일치
| `400`
| 사업자등록번호·대표자명·개업일자가 국세청 등록 정보와 일치하지 않습니다.

| 미등록 사업자번호
| `400`
| 국세청에 등록되지 않은 사업자등록번호입니다.

| 휴업자
| `400`
| 휴업 중인 사업자는 등록할 수 없습니다.

| 폐업자
| `400`
| 폐업한 사업자는 등록할 수 없습니다.

| 이미 등록된 사업자번호
| `409`
| 이미 사용 중인 사업자번호입니다.

| 일일 시도 한도 초과
| `429`
| 하루 인증 시도 횟수를 초과했습니다. 내일 다시 시도해주세요.

| 국세청 시스템 장애·점검
| `503`
| 국세청 시스템 점검 등으로 확인이 지연되고 있습니다. 잠시 후 다시 시도해주세요.
|===

IMPORTANT: `503` 은 사용자 입력 문제가 아닙니다. 입력값을 고치라는 안내 대신 재시도를 안내해야 합니다.

[[company-reverification]]
=== 사업자 재인증

이미 등록·인증된 회사의 *대표자명·개업일자* 를 국세청에 다시 확인해 갱신합니다. 소유자(멤버)만 호출할 수 있습니다.

선행 인증(<<company-verification>>)과 결정적으로 다른 점은 *사업자번호를 요청으로 받지 않는다* 는 것입니다.
사업자번호는 DB 에 저장된 값(최초 인증본에서 온 불변값)을 그대로 국세청에 질의합니다 — 재인증 때 번호를 새로
입력받으면 오타나 타사 번호로 인증을 갈아끼워 "국세청 확인" 배지를 탈취할 수 있기 때문입니다. 국세청 연동은 그
회사의 존재·상태만 알려줄 뿐 소유권을 증명하지 않으므로, 번호는 절대 바뀌지 않게 고정합니다.

국세청 등록 정보가 바뀌었을 수 있으므로 서버는 이전 값과 비교하지 않습니다. 새로 입력한 대표자명·개업일자가
재확인을 통과하면 그대로 회사 정보를 덮어쓰고 인증 시각(`verifiedAt`)을 새로 찍습니다.

이 경로의 쓰임은 두 가지입니다.

. 국세청 정보(대표자명·개업일자)가 변경됐을 때의 갱신 창구. 국세청 인증을 받은 회사는 일반 수정(<<company-update-basic>>)으로
  이 두 값을 바꿀 수 없으므로(`400` 국세청 인증을 받은 회사는 대표자명·개업일자를 수정할 수 없습니다), 재인증을 통해서만 갱신합니다.
. 최초 인증 후 *1년* 이 지나면 재인증을 유도합니다(주기 갱신). 1년 경과를 감지해 재인증을 요청하는 이벤트 발행은 추후 과제이며,
  이 API 자체는 언제든 호출할 수 있습니다.

일일 시도 한도(사용자당 하루 5회)와 감사 로그는 선행 인증과 같은 집계를 공유합니다.

[[company-create]]
=== 회사 등록 (유저 자가등록)

인증된 유저가 본인 회사를 등록합니다. 등록자는 즉시 소유자(`OWNER`)가 되며, 회사는 `FREE` 등급으로 시작합니다.
변경 요청이므로 세션 쿠키와 CSRF 토큰이 필요합니다(<<overview-auth>> 참고).

자가등록은 <<company-verification>> 을 먼저 통과해야 하며, 발급받은 `verificationId` 를 함께 보냅니다.
등록이 완료되면 회사는 사업자 인증 완료(`businessVerified=true`) 상태로 생성됩니다.

NOTE: 요청 본문에 `businessNumber`/`ceoName`/`establishmentDate` 는 없습니다. 이 세 값은 인증 레코드에서만 채워지며,
`establishmentDate` 에는 국세청이 검증한 개업일자가 들어갑니다. 인증 후에는 대표자명·개업일자를 수정할 수 없습니다(<<company-update>>).

요청 본문은 회사 본체와 부속(연락처/이미지/레퍼런스/소재·설비·태그/링크 마스터 ID)을 한 번에 받습니다.
`companyName` 외 항목은 임시저장(DRAFT) 호환을 위해 모두 선택이며, 일부 항목은 등급별 정책 제한을 받습니다.

인증 식별자가 유효하지 않으면 등록이 거부됩니다 — 본인이 받은 것이 아니면 `400`(유효한 사업자 인증 정보가 없습니다),
만료됐으면 `400`(사업자 인증이 만료되었습니다), 이미 다른 회사에 썼으면 `409`(이미 회사 등록에 사용된 사업자 인증입니다).

| 존재하지 않는 인증 ID | 존재하지 않는 인증이 포함되어 있습니다.
| 존재하지 않는 국가 ID | 존재하지 않는 국가가 포함되어 있습니다.
| 존재하지 않는 국내 지역 ID | 존재하지 않는 국내 지역이 포함되어 있습니다.
| 존재하지 않는 산업군 ID | 존재하지 않는 산업군이 포함되어 있습니다.
|===

[[company-search]]
=== 회사 목록/검색 (공개)

회사를 검색·브라우즈합니다. 누구에게나 열려 있는 공개 API 로, 인증이 필요 없습니다.

검색은 세 축으로 조합됩니다(모두 선택적, 지정한 것만 AND 로 적용):

* *통합 키워드* (`keyword`): 회사명·소개·레퍼런스·설비·소재 등 전체 텍스트에 부분일치. 공백으로 나눈 여러 토큰은 모두 포함(AND).
* *고급검색* (`companyName`/`content`/`reference` 등): 지정한 필드에만 부분일치.
* *패싯* (`certificationIds`/`industryIds`/`categoryIds`): 선택한 ID 중 하나라도 보유한 회사(차원 내 OR). 카테고리는 대분류를 고르면 그 후손 서브트리까지 매칭됩니다. 인증 패싯에 '기타'(`type=ETC`) 를 넣으면 이름을 무엇으로 적었든 직접 입력한 인증을 가진 회사가 모두 잡힙니다 — 검색은 마스터 ID 로만 매칭하고 입력한 이름은 보지 않습니다.

정렬은 스팟라이트 고정 → 추천 → 최신 순으로 고정이며, 결과는 요약 카드 형태로 페이징됩니다.

NOTE: 카드의 `spotlight` 는 *관리자가 수동으로 고정(pin)했는지* 를 뜻하며, 메인 화면 노출 여부가 아닙니다.
요금제 자격으로 메인에 노출되는 회사는 이 값이 `false` 입니다. 메인 화면 노출 목록은 <<company-showcase>> 를 사용하세요.

=== 메인 화면 노출 영역 (공개)

메인 화면의 *스팟라이트* 와 *추천 기업* 두 영역을 한 번에 조회합니다. 누구에게나 열려 있는 공개 API 입니다.

목록/검색(<<company-search>>) 결과를 받아 프론트에서 플래그로 걸러내지 마세요 — 노출 후보가 화면의 자리 수보다
많아지는 순간 어느 회사가 잘릴지 프론트가 알 수 없고, 한쪽 영역이 통째로 비어 보일 수 있습니다.
어느 회사가 어느 자리를 차지하는지는 서버가 정해서 내려줍니다.

응답은 페이지가 아니라 *자리 수만큼의 고정 리스트* 라 `pageInfo` 가 없습니다. 각 영역의 자리 수는 서버 설정값입니다.

*스팟라이트 영역에 담기는 회사*

* *요금제 자격* — 유료 활성 구독(`PREMIUM`/`ENTERPRISE`, 미만료). 관리자 조작 없이 자동으로 포함되고,
  구독이 만료되면 자동으로 빠집니다. 체험(`TRIAL`)과 관리자 등록(`ADMIN_EXEMPT`)은 포함되지 않습니다.
* *관리자 고정(pin)* — `spotlight = true`. 요금제와 무관하게 노출해야 하는 제휴·이벤트용 통로이며,
  자격분보다 앞에 배치됩니다.

*추천 영역* 은 등급과 무관한 순수 관리자 큐레이션(`featured = true`)입니다.

두 영역에 같은 회사가 함께 나올 수 있습니다(고정 + 추천). 의도된 동작이므로 프론트에서 중복 제거하지 않습니다.

*카드 배경 두 필드*

카드에는 로고(`logoUrl`) 말고도 배경에 쓰는 값이 두 개 더 실립니다. 둘 다 선택이라 `null` 로 내려올 수 있고,
서버는 대체값을 만들어 주지 않습니다 — 없을 때 무엇을 그릴지는 화면이 정합니다.

* `coverImageUrl` — 카드 커버 사진. 로고와 다른 자리입니다(로고는 정사각 배지, 커버는 카드 배경에 깔리는 와이드 사진).
  같은 이미지가 스팟라이트(거의 정사각)와 추천 카드(가로로 긴 띠)에서 서로 다른 비율로 잘리므로 `object-fit: cover` 를 전제합니다.
  회사 갤러리(상세 응답의 `galleryImages`)와도 별개의 값입니다.
* `brandColor` — 스팟라이트 배너 배경색(`#RRGGBB`). 배너 위 텍스트 대비는 화면이 명도로 판단하세요.

회사 멤버 본인이 자기 회사의 기본 정보를 부분 수정합니다. 변경 요청이므로 세션 쿠키와 CSRF 토큰이 필요합니다(<<overview-auth>> 참고).

본체 스칼라 필드만 수정하며, 부속 컬렉션(태그·소재·설비·연락처·이미지·레퍼런스·링크 마스터)은 <<company-update-collections>> 로 따로 교체합니다.

* *비우기(clear) 규약*: 선택 문자열 필드는 빈 문자열(`""`)을 보내면 값을 비웁니다. 필수 필드(회사명·대표자·주소 등)는 빈 문자열로 비울 수 없어 `400` 이 반환됩니다. 날짜·enum 은 비우기를 지원하지 않습니다(값이 오면 교체만).
* 시스템 플래그(`verified`/`featured`/`spotlight`/`spotlightOrder`/`deleted`)·사업자번호·등록 provenance 는 이 API 로 바꿀 수 없습니다(요청 필드에서 제외).
* `coverImageUrl` 은 선택 필드라 `""` 로 비울 수 있습니다. 필수인 `logoUrl` 과 다릅니다.
* `brandColor` 는 `#RRGGBB` 형식만 받습니다(`""` = 비우기). 색 이름·축약형(`#RGB`)·`rgb()` 표기는 `400` 입니다.

=== 회사 부속 컬렉션 교체 (소유자)

회사 멤버 본인이 자기 회사의 부속 컬렉션을 *통째로 교체(PUT)* 합니다. 변경 요청이므로 세션 쿠키와 CSRF 토큰이 필요합니다(<<overview-auth>> 참고).

각 컬렉션은 독립된 엔드포인트로 나뉘며, 요청 본문의 리스트가 기존 컬렉션을 완전히 대체합니다(부분 수정이 아니라 전체 교체). *빈 배열(`[]`)을 보내면 해당 컬렉션을 전부 비웁니다.* 표시 순서(`displayOrder`)는 클라이언트가 보내지 않고 서버가 배열 인덱스로 재부여합니다. 성공 응답은 본문 없이 `success` 플래그만 내려갑니다.

[cols="3,4,4"]
|===
| 엔드포인트 | 본문 | 설명

| `PUT /api/v1/companies/{id}/tags` | `["문자열", ...]` | 태그명 목록
| `PUT /api/v1/companies/{id}/materials` | `["문자열", ...]` | 취급 소재명 목록
| `PUT /api/v1/companies/{id}/equipment` | `["문자열", ...]` | 보유 설비명 목록
| `PUT /api/v1/companies/{id}/contacts` | `[{연락처}, ...]` | 담당자 연락처 (현재 1건 제한)
| `PUT /api/v1/companies/{id}/images` | `[{이미지}, ...]` | 갤러리 이미지 (DETAIL 타입만 허용)
| `PUT /api/v1/companies/{id}/references` | `[{레퍼런스}, ...]` | 프로젝트 레퍼런스 (현재 1건 제한, 등급별 이미지 장수 제한)
| `PUT /api/v1/companies/{id}/categories` | `[숫자, ...]` | 카테고리 ID 목록 (등급별 개수 제한)
| `PUT /api/v1/companies/{id}/certifications` | `[{인증}, ...]` | 인증 목록. 다른 링크와 달리 ID 배열이 아니라 `{"certificationId": 숫자, "customName": "문자열"}` 객체 배열입니다 (아래 참고)
| `PUT /api/v1/companies/{id}/industries` | `[숫자, ...]` | 산업군 ID 목록
| `PUT /api/v1/companies/{id}/countries` | `[숫자, ...]` | 수출 국가 ID 목록
| `PUT /api/v1/companies/{id}/regions` | `[숫자, ...]` | 국내 지역 ID 목록
|===

[NOTE]
====
*인증(`certifications`)만 본문 형태가 다릅니다.* 마스터 목록에 없는 인증을 회사가 직접 적어 넣을 수 있기 때문입니다.

* 목록에서 고른 인증: `{"certificationId": 3}` — `customName` 을 보내면 거부됩니다.
* 목록에 없는 인증: 공개 옵션 목록(`GET /api/v1/certifications`)의 *'기타'(`type=ETC`)* 항목 ID 를 보내고 `customName` 에 인증명을 적습니다. `customName` 없이 '기타'만 보내면 거부됩니다.
* '기타'는 이름만 다르면 여러 건 보낼 수 있습니다. 같은 인증 + 같은 이름은 1건으로 접힙니다(앞뒤 공백은 무시).
* 조회 응답의 `certifications[].certificationName` 에는 직접 입력한 이름이 그대로 실려 옵니다 — 프론트에서 '기타'와 입력값을 합칠 필요가 없습니다.

등록(`POST /api/v1/companies`, `POST /api/v1/companies/my`)의 `certifications` 필드도 같은 형태입니다.
====

[[company-like-favorite]]
=== 회사 좋아요 / 즐겨찾기 (인증)

로그인한 사용자가 회사를 좋아요/즐겨찾기 하거나 해제합니다. 변경 요청이므로 세션 쿠키와 CSRF 토큰이 필요합니다(<<overview-auth>> 참고).

토글이 아니라 *등록(`PUT`)* 과 *해제(`DELETE`)* 로 동사를 분리했습니다. 덕분에 각 요청이 *멱등* 합니다 — 같은 요청을 여러 번 보내도 결과 상태가 한 방향으로만 수렴하며, 네트워크 재시도나 중복 클릭에도 안전합니다.

* 이미 좋아요/즐겨찾기한 상태에서 다시 `PUT` 을 보내도 오류가 아니라 `204` 로 응답합니다(서버가 중복 등록을 무시). 이미 도달한 상태를 재확인하는 것은 충돌이 아니므로 `409` 를 반환하지 않습니다.
* 없는 상태에서 `DELETE` 를 보내도 `204` 로 응답합니다.
* 성공 응답은 항상 본문 없는 `204 No Content` 입니다. 현재 상태(`likedByMe`/`favoritedByMe`)는 회사 조회 API(<<company-search>>, <<company-public-detail>>)가 내려주므로 이 API 는 본문을 되돌려주지 않습니다.

[cols="3,2,4"]
|===
| 엔드포인트 | 성공 | 설명

| `PUT /api/v1/companies/{id}/like` | `204` | 좋아요 등록 (멱등)
| `DELETE /api/v1/companies/{id}/like` | `204` | 좋아요 해제 (멱등)
| `PUT /api/v1/companies/{id}/favorite` | `204` | 즐겨찾기 등록 (멱등)
| `DELETE /api/v1/companies/{id}/favorite` | `204` | 즐겨찾기 해제 (멱등)
|===

아래는 좋아요 등록/해제를 대표 예시로 든 것입니다. 즐겨찾기(`/favorite`)도 경로만 다를 뿐 요청/응답 형태가 동일합니다.

[[admin-company-list]]
=== 회사 목록 (관리자)

관리자가 전체 회사를 목록으로 조회합니다. 기본은 *삭제된 회사까지 포함한 전체* 이며, 최신 등록순으로 페이징됩니다.
공개 목록과 달리 각 카드에 운영 필드(삭제 여부·소유자 id·등록 출처·등록 시각)와 구독 요약이 함께 내려갑니다.

구독 요약은 *지금 유효한 등급*(`effectiveGrade`) + *상태*(`status`) + *만료일*(`expiresAt`) 3종입니다.
`status` 로 체험(`TRIAL`)·결제(`ACTIVE`)·면제(`ADMIN_EXEMPT`)를 목록에서 바로 구분할 수 있습니다.
`effectiveGrade` 는 만료된 유료 구독을 `FREE` 로 강등한 "현재 실제 적용 등급"이며, 계약 원본 등급은 목록에 싣지 않고 구독 수정(<<admin-company-subscription>>)에서 다룹니다.

다음 조건으로 좁힐 수 있으며, *지정한 것만 AND(교집합)* 로 적용됩니다(미지정 = 상관없음):

* *상태 필터* (`verified`/`featured`/`spotlight`): `true`/`false` 로 해당 값만. 생략하면 그 축은 무시됩니다. 예) `verified=true&featured=true` 면 둘 다 참인 회사만(스팟라이트는 무관). `spotlight` 는 *수동 고정(pin)* 축이라, 요금제 자격으로 메인에 노출 중인 회사는 `spotlight=false` 로 잡힙니다.
* *삭제 필터* (`deleted`): 생략하면 삭제 포함 전체, `true` 면 삭제된 회사만, `false` 면 활성 회사만.
* *회사명* (`companyName`): 부분일치.
* *소유자* (`ownerUserId`): 소유 유저 ID 정확 일치(미연동 회사는 제외됨).

[[admin-company-flags]]
==== 운영 플래그 조정 (관리자)

관리자가 회사의 운영 플래그 — 인증(`verified`)·추천(`featured`)·스팟라이트(`spotlight`) — 를 조정합니다. `ADMIN` 권한이 필요하며 소유 여부와 무관합니다.

셋 다 등록 시 `false` 로 시작하며, 요청은 *sparse* 입니다 — 보낸 필드만 목표값(`true`/`false`)으로 설정하고 생략한 필드는 그대로 둡니다. 목표 상태를 지정하는 *멱등* 요청이라 같은 값으로 여러 번 보내도 안전합니다. (이 플래그들은 검색 도큐먼트가 아니라 회사 원본에서 정렬에 쓰이므로 재색인이 필요 없습니다.)

IMPORTANT: `spotlight` 는 *메인 노출을 켜는 스위치가 아니라 수동 고정(pin)* 입니다. 유료 고객(`PREMIUM`/`ENTERPRISE`)은
이 플래그를 켜지 않아도 구독만으로 메인에 노출되며(<<company-showcase>>), 구독이 끝나면 자동으로 빠집니다.
따라서 *유료 계약 고객에게는 이 플래그를 쓰지 마세요* — 구독(<<admin-company-subscription>>)을 설정하는 것이 맞습니다.
pin 은 요금제 밖에서 노출해야 하는 제휴·이벤트용이며, 켜 두면 구독과 무관하게 계속 노출되고 자동으로 꺼지지 않습니다.
이 구분을 지켜야 나중에 "돈 낸 고객"과 "무료로 띄워준 곳"을 데이터로 구별할 수 있습니다.

[[admin-company-verification-revoke]]
==== 사업자 인증 회수 (관리자)

관리자가 회사의 국세청 사업자 인증을 회수합니다(사칭 신고 등). `ADMIN` 권한이 필요하며 소유 여부와 무관합니다.

WARNING: 위 <<admin-company-flags>> 의 `verified` 와는 *다른 축* 입니다. `verified` 는 에디터 선정 큐레이션 배지이고,

회수 사유(`reason`)는 필수입니다. 인증은 향후 첫 달 혜택의 자격 조건이 되므로 되돌린 근거가 반드시 남아야 합니다.

[[admin-company-subscription]]
=== 회사 구독 조회/수정 (관리자)

관리자가 임의 회사의 구독을 조회하고 수정합니다. 소유 여부와 무관하게 모든 회사를 대상으로 하며, `ADMIN` 권한이 필요합니다(<<overview-auth>> 참고).
구독의 주인은 회사(1:1)이므로 구독 관리도 회사 단위로 이뤄집니다 — 목록에서는 파생 등급 배지만 노출하고, 배지 옆 수정 버튼으로 이 조회/수정을 띄우는 흐름을 상정합니다.

조회 응답에는 사용자용 구독 조회(<<company-subscription>>)와 같은 필드에 더해 감사용 타임스탬프(`createdAt`/`updatedAt`)가 포함됩니다.

수정은 `grade`/`status`/`expiresAt` 세 필드를 관리자가 직접 지정하는 *전체 교체(full-replace)* 입니다. 수정 팝업이 세 필드를 항상 채워 보내는 것을 전제로 합니다.

* `grade`/`status` 는 필수입니다.
* `expiresAt` 은 만료일이며, `null` 이면 *무기한*(만료 없음)을 뜻합니다.
* `startedAt`(시작일)은 팩트라 수정 대상이 아닙니다(기존값 보존).
* `effectiveGrade`(지금 유효한 등급)는 `grade`/`status`/`expiresAt` 에서 파생되므로 별도로 저장·수정하지 않습니다. 예를 들어 유료 등급이라도 `expiresAt` 이 과거이면 조회 시 `effectiveGrade` 는 `FREE` 로 내려갑니다.

NOTE: 이 API 는 구독 테이블만 변경합니다. 등급을 낮춰도 이미 초과된 기존 데이터(카테고리 수 등)를 소급해서 잘라내지 않으며, 해당 컬렉션을 다음에 수정하는 시점에 등급 정책이 적용됩니다.

=== 폼 입력 제약 조회

폼 하나에 걸린 입력 제약을 내려줍니다. 프론트가 저장을 누르기 전에 서버와 같은 기준으로 막고, 같은 문구를
띄우기 위한 것입니다. 값은 요청 DTO 에 붙은 검증 애너테이션에서 그대로 뽑으므로 서버가 실제로 강제하는
규칙과 어긋나지 않습니다. 세션 쿠키가 필요합니다(<<overview-auth>> 참고).

`fields` 는 화면의 폼 순서(요청 DTO 선언 순서)로 정렬돼 있고, `field` 이름은 검증 실패 응답의
`errors[].field` 와 같은 어휘입니다 — 폼을 그릴 때와 400 을 받았을 때 같은 키로 입력칸을 찾으면 됩니다.
제약이 하나도 없는 칸(enum 등)은 목록에 나오지 않습니다.

여기서 내려가는 것은 **정적 제약뿐**입니다. 프론트가 폼을 막는 근거는 세 갈래이고 나머지 둘은 출처가 다릅니다.

* 등급이 정하는 한도(카테고리 개수 · 이미지 장수)는 회사마다 달라 이 응답에 담기지 않습니다.
등록 폼은 사업자 인증 응답의 `limits`, 수정 폼은 구독 조회의 `limits` 를 봅니다.
이 응답의 개수 상한은 등급과 무관한 절대 천장이므로, **둘 중 작은 쪽**이 실제 한도입니다.
* 중복 여부(이메일 · 사업자번호)는 값을 봐야 알 수 있어 사전 검증이 불가능합니다. 전용 확인 엔드포인트를 왕복합니다.
